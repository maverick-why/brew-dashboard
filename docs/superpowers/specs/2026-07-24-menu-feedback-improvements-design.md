# 客人反馈：酒单三项改进 — Design

## Problem

客人对目前的电视酒单提出三点反馈：
1. 酒花类啤酒的新鲜度信息（上枪多少天）看不到
2. 左屏有活动展示区，右屏没有对等的内容区，显得不对称、也少了一个可以讲故事的地方
3. 国旗图标太小看不清，且对中国产的酒来说"国旗"这个维度本身没有信息量（都一样是🇨🇳）

三项彼此独立，改动的文件有重叠（`menu.html` 渲染、`admin.html` 编辑、`api/menu-edit.js` / `api/menu-public.js` 数据），因此合并成一份设计文档，但作为三个独立可交付的功能来实现。

## Scope

- 酒单卡片新增「上枪天数」展示，按酒款手动开关
- 右屏新增一个与左屏活动区对称的「本店趣味数据榜」独立展示区
- 「国旗」字段改为纯文字展示，中国产地额外录入城市名

不涉及：POS/会员系统的实时数据接入（见需求二的"数据来源"说明）、酒单卡片整体重新排版、深色卡片视觉改版（`style-editor-prototype.html` 是用户另一个独立在做的实验，与本次改动无关，不在本文档处理范围内）。

## 需求一：酒花类啤酒上枪天数

### 数据模型

在现有的 per-tap 菜单数据（Redis `brew_dash_menu_v1`，每个 tap 一条 flat object）上新增两个字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `show_tap_day` | boolean | 是否显示上枪天数，手动开关，默认 false |
| `tap_date` | string (YYYY-MM-DD) | 上枪日期，`show_tap_day` 开启时必填，默认当天 |

不做"酒花类"关键词自动识别——`style` 是自由文本，容易漏判/误判，直接交给店员手动判断更可靠。

### 计算规则

`dayN = 今天 - tap_date`（按自然日整数差），**上枪当天 = Day 0**，之后逐日 +1。

不设上限、不自动过期。如果店员觉得某天之后展示天数已经没有意义（比如卖了 10 天还挂着 "Day 10"），由店员手动关闭 `show_tap_day` 开关，前端就不再显示——不需要系统判断"多少天算不新鲜"。

### 展示位置

复用卡片现有的中英文分区结构，不额外占地方、不新增视觉元素：

- **中文区**：`.beer-style`（酒款风格）下方新增一行 `上枪时间 Day {N}`
- **英文区**：现有的 `.alc-info`（`ALC 6.8%  ·  IBU 35`）后面追加 `· On Tap Day {N}`

只有 `show_tap_day === true` 时才渲染这两处；否则卡片布局和现在完全一样。

### 涉及文件

- `admin.html`：`MENU_FIELDS` 增加开关（checkbox）+ 日期输入两个字段
- `api/menu-edit.js` / `api/menu-public.js`：透传 `show_tap_day` / `tap_date` 两个新字段（无需 schema 迁移，Redis 存的是自由 JSON）
- `menu.html`：`makeCard()` 渲染逻辑 + 对应 CSS（中文区新增一行、英文区 alc-info 文本拼接）

## 需求二：右屏「本店趣味数据榜」

### 布局

镜像左屏结构。当前：

- `dual-screen-left`：3 列（活动区 1 列 + 酒单 2 列）
- `dual-screen-right`：3 列（酒单 3 列，无独立区）

改为：

- `dual-screen-right`：3 列（酒单 2 列 + 新区域 1 列），新区域宽度与左屏活动区一致，位于**右屏最右侧**
- `dual-preview`（后台总预览，6 列画布）相应地在最右侧新增第 6 列

酒单可展示的总列数从右屏 3 列减少到 2 列，tap 总数上限需要相应下调（原本 `dual-screen-right` 单独跑 3 列 × N 行，减少 1 列后每屏可容纳的酒款数变少；具体行数/换算在实现阶段按当前 `screenCount` / 分页逻辑核对，不在设计阶段锁死数字）。

### 视觉

不沿用中间酒单卡片的表格式布局（无论是浅灰版还是深色版），刻意做出区别，让客人一眼看出这是「信息区」而不是酒单的一部分：

- 背景延用左屏活动区已有的深色渐变（`linear-gradient(135deg, #101722 0%, #173725 58%, #0b1118 100%)`），白字，与左侧活动区风格呼应，形成左右对称的"两侧信息区"视觉语言
- 每条内容做成独立小卡片（浅色半透明背景 `rgba(255,255,255,.05)`，圆角），卡片左侧 4px 色条标出类别：
  - 🟢 销售数据　🌸 会员数据　🟠 清桶记录　🟣 店员观察（四色对应四类数据来源，具体色值取现有色板，不新增配色系统）
  - 每条结构：标题（小字）+ 结果值（大字，通常是酒名）+ 可选的右侧小字说明（仅需要额外解释时填写，不强制）
- 区域底部统一放一个颜色图例（说明四种颜色分别代表什么），不在每条卡片上重复贴标签
- 条数上限 **12 条**，固定字号、不做自动缩放（TV 是扫一眼看的场景，字缩太小可读性优先级更高）；后台编辑超过上限时提示"超出展示容量，请精简"

### 内容与数据来源

系统**不做实时统计**，不接入 POS/会员系统。用户线下导出销售数据、自行按下面的口径分析，把结论手动录入后台（类似当前活动区 `poster_items` 的编辑方式，但作为一个固定展示的列表，不做轮播）。

三级可信度分类（用户提出，作为后台录入时的内部方法论，不是系统强制校验）：

1. **交易数据榜**（最可靠）——直接来自收银系统的销售记录：销售杯数/金额、点单时间、订单人数、SKU、开桶/售罄时间、复购记录
2. **会员画像榜**（有条件使用）——需要会员主动填写性别/生日等信息且能与订单关联；命名要准确（如"女性会员人气王"而非"女生最爱"），避免过度推断（一人代付整桌订单时，系统只知道付款人信息，不能判断每杯酒的实际饮用者）
3. **店员观察榜**（不伪装成数据）——无法用销售数据得出的主观印象（如"最适合一个人喝的酒"），必须标注来源是店员观察/吧台印象，不能包装成统计结果

每条录入的字段：

| 字段 | 说明 |
|---|---|
| `category` | 四选一：销售数据 / 会员数据 / 清桶记录 / 店员观察（决定左侧色条颜色） |
| `title` | 展示标题（如"女性会员人气王"） |
| `value` | 结果（如"决心"），支持追加小字后缀（如"· 3天"） |
| `caption` | 可选，右侧小字说明，仅需要时填写 |
| `internal_note` | 可选，仅后台可见的完整口径说明（数据周期/统计对象/去重规则等），供店员应对顾客提问时查阅，不在电视上展示 |

### 涉及文件

- 新增数据表（建议 Supabase 新表 `fun_fact_items`，字段对应上表 + `sort_order` + `enabled`，结构类似 `poster_items` 但不需要 `duration_sec`/`starts_at`/`ends_at` 这些轮播相关字段）
- 新增 API：`GET /api/fun-facts-public`（公开读取，enabled 且按 sort_order 排序）+ 后台 CRUD（可复用 `poster-admin` 的鉴权模式）
- `admin.html`：新增一个类似"活动区管理"的编辑面板（增删改 + 拖拽排序），含条数上限校验
- `menu.html`：`dual-screen-right` 新增 `#funFactZone`，渲染逻辑与样式（参照 `.poster-zone` 结构新写一套，不复用 `.card` 系统）

## 需求三：产地信息（国旗改文字）

### 数据模型

沿用现有 `flag` 字段（存的是 emoji，通过 `admin.html` 里的 `FLAG_OPTIONS` 下拉选择），新增：

| 字段 | 类型 | 说明 |
|---|---|---|
| `city` | string | 自由文本，仅产地为中国时使用，默认空 |

### 展示规则

- `flag !== "🇨🇳"`：显示 `FLAG_OPTIONS` 里对应的中文国家名文字（如"比利时"），替代原来的 emoji
- `flag === "🇨🇳"`：显示 `city` 字段内容；若 `city` 为空，暂时留空或 fallback 显示"中国"（避免上线当天大量酒款突然空白）

`.brewery-tag .flag` 的展示方式从 emoji 图标改为文字 span，样式需要重新调整（现有 CSS 是按 emoji 尺寸做的间距，文字长度不固定，需要适配换行/截断）。

### 迁移

- 非中国的现有数据：直接用 `FLAG_OPTIONS` 做 emoji → 文字的映射，无需人工介入
- 中国的现有数据：`city` 字段默认空，需要店员在后台逐个手动补录（不做批量猜测，酒厂名不能可靠地推断城市）

### 涉及文件

- `admin.html`：`FLAG_OPTIONS` 选择器逻辑不变（还是选国家），新增一个「城市」文本输入框，仅当选中"中国"时显示/启用
- `api/menu-edit.js` / `api/menu-public.js`：透传新增的 `city` 字段
- `menu.html`：`brewery-tag` 渲染逻辑改为文字优先，CSS 调整

---

## Out of scope

- 不做 POS/会员系统实时数据接入（需求二的内容全部手动录入）
- 不做"酒花类"关键词自动识别（需求一用手动开关）
- 不做城市下拉库/城市自动补全（用自由文本框）
- 不涉及 `style-editor-prototype.html` 里的深色卡片视觉改版
- 不做上枪天数的自动过期/隐藏逻辑（店员手动关开关）

## Deployment note

`main` 分支自动部署到店内电视。三个需求分别改动 `menu.html`（渲染，客人直接可见）和 `admin.html`（后台编辑），上线前需要完整 diff 这两个文件，参照现有项目惯例（无独立 staging 环境）。
